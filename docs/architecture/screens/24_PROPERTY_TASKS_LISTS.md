# Roundhouse Property Tasks / Lists

## Purpose

**Tasks / Lists** is the second right-edge working screen inside the Property Entity.

Its home is:

**Property Entity → Tasks / Lists**

It answers:

**What smaller things are we keeping track of at this Property?**

Tasks / Lists is intentionally lighter than Property Work.

It is for simple organization that does not need the full responsibility, execution, CAPTURE, verification, and lifecycle structure of a Work item.

---

# 1. Position Inside the Property Entity

The Property Entity right-edge order remains:

1. **Work**
2. **Tasks / Lists**
3. **Maintenance**
4. **Vault**

Tasks / Lists keeps the same physical second position used on the personal Command Center so the user does not need to relearn where lightweight organization lives.

The scope changes with context:

**Command Center Tasks / Lists = my working lists and the Property/job lists available to me.**  
**Property Tasks / Lists = lightweight tasks and lists available to me at this Property.**

---

# 2. Governing Boundary — Work vs Tasks / Lists

This distinction is critical.

## Work

Use **Work** when the item has meaningful job structure such as:

- a requester;
- an assignee / responsible party;
- execution status;
- due work that needs operational tracking;
- CAPTURE evidence;
- Calendar scheduling;
- verification;
- related Estimate / Invoice;
- significant Asset or Property service history.

## Tasks / Lists

Use **Tasks / Lists** when the information is lightweight, such as:

- a quick one-off task;
- a punch item that does not yet require a full Work Record;
- a shopping / materials list;
- a checklist;
- a short reminder;
- a collection of small items being tracked together.

The governing test is:

**If we mainly need to remember it, check it off, or keep a small group of items organized, it belongs in Tasks / Lists. If we need to manage a job, it belongs in Work.**

---

# 3. Working-Sheet Behavior

Tasks / Lists opens as a large Property-scoped working sheet over the Property Timeline.

It should not feel like a separate project-management application.

The Property context remains clear and the right-side rail remains available.

At the top:

**Tasks / Lists**  
Property name beneath it  
**Search**                 **+ New**

The **+ New** control opens a simple choice:

**Task | Checklist | List**

Only actions permitted to the current person are available.

---

# 4. Three Simple Modes

The screen uses three lightweight internal modes:

**Tasks | Checklists | Lists**

These are organization modes, not separate data silos.

A simple item can move or be reclassified when useful without creating duplicate Records.

---

## 4.1 Tasks

Tasks contains small Property-scoped things that need to be remembered or checked off but do not justify a Work item.

Examples:

- measure pantry shelf depth;
- confirm paint sample location;
- replace missing cabinet bumper;
- photograph attic label;
- ask homeowner which finish they prefer;
- bring extra drop cloths tomorrow.

A Task may contain only the fields that are useful:

- title;
- optional short note;
- optional due date;
- optional lightweight assignee when permitted;
- optional related room / area;
- optional related Asset;
- complete / incomplete state.

Tasks should stay visually compact.

If the item grows into a real job, it can be deliberately **Convert to Work** rather than accumulating Work-level complexity inside Tasks.

---

## 4.2 Checklists

Checklists are reusable or one-time collections where completion of several small steps matters.

Examples:

- arrival checklist;
- homeowner turnover checklist;
- final walkthrough;
- seasonal prep;
- room punch checklist;
- jobsite closeout checklist.

A checklist can show:

- title;
- optional description;
- item count / progress;
- optional related area / Asset;
- optional owner / assignee where useful;
- individual checkable items.

Checklists remain lightweight. If the checklist is actually governing repeatable Property care, it belongs in **Maintenance** instead.

The distinction is:

**Checklist = a collection of steps.**  
**Maintenance Rule = a durable recurring care obligation.**

---

## 4.3 Lists

Lists are flexible collections of related information or items.

Examples:

- Shopping;
- Materials;
- Punch List;
- Paint Samples;
- Hardware Needed;
- Homeowner Selections;
- Things to Verify.

A List may contain:

- title;
- optional note / purpose;
- list items;
- checked / unchecked state where appropriate;
- optional quantities;
- optional short item notes;
- optional related room / area.

A List should not require every item to become a separate Task Record.

---

# 5. Master View

Opening Tasks / Lists should not dump the contents of every list onto the screen.

The default view is a clean index of relevant Property-scoped items.

It may show:

- open Tasks first;
- active Checklists;
- named Lists;
- recently used items where useful.

Each row / card should remain compact.

Example:

**Punch List — Guest Bath**  
6 items · 4 complete

Example:

**Materials**  
8 items · updated today

Example:

**Measure Pantry Shelf Depth**  
Due tomorrow

Tapping an item opens its detail rather than expanding every item at once.

---

# 6. Task Detail

Task Detail should remain extremely simple.

It may show:

- task title;
- short note;
- complete / incomplete state;
- due date if one exists;
- lightweight assignee if one exists;
- related area / Asset;
- created by / last updated where useful.

Primary actions can include:

- Complete;
- Edit;
- Convert to Work;
- Share / change audience when authorized.

Do not add Work-level status chains to Task Detail.

---

# 7. Checklist Detail

Checklist Detail shows:

- checklist title;
- optional description;
- progress such as **4 of 6 complete**;
- checkable items;
- optional short notes on individual items;
- optional related area / Asset.

The user should be able to check items quickly without opening separate detail pages for every line.

If an individual checklist item becomes a substantial job, it may be converted to Work while remaining visibly related to the source checklist.

---

# 8. List Detail

List Detail should feel like a clean working pad.

The top shows:

- list name;
- audience / ownership state when relevant;
- **+ Add Item**.

Each line may support:

- item text;
- quantity where useful;
- checked / unchecked state;
- short note;
- drag / reorder where helpful.

The interaction should remain fast enough for jobsite use with one hand.

---

# 9. Privacy and Audience

Property context does **not** mean universal Property visibility.

This rule from the Command Center list architecture carries forward.

A Property-related Task, Checklist, or List may be:

- **Private / Internal** — available only to the person or authorized Business participants;
- **Shared with Property** — deliberately shared with specific authorized Property participants;
- **Property-owned / governed** — intentionally part of the shared Property workspace according to permission.

The audience must be visually clear.

Roundhouse should not rely on a tiny privacy icon to communicate a consequential difference.

Examples of clear language:

**INTERNAL — DMT DESIGN BUILD**  
**SHARED WITH PROPERTY**

An internal Business list must not become homeowner-visible through an accidental single tap.

Sharing into the Property-visible space requires a deliberate action and confirmation where the visibility change is meaningful.

---

# 10. Personal Lists vs Property Lists

A person's private personal list remains on their Command Center.

Entering a Property does not automatically move or expose that list.

A personal list may reference the Property and still remain private.

Only information deliberately shared, governed as Property information, or otherwise legitimately available through current permissions appears in the Property Tasks / Lists screen.

This preserves the core rule:

**Association with a Property does not automatically grant Property participants access.**

---

# 11. Notes and Reminders

Short notes and reminders may live inside Tasks, Checklists, and Lists rather than becoming additional permanent tabs.

Examples:

- task note;
- list-item note;
- due reminder;
- short instruction;
- internal reminder tied to a Property item.

A reminder can surface in Daily Grind or other appropriate personal working views without moving ownership of the underlying item.

A durable Property fact should not be buried indefinitely in a list note. If the information becomes permanent Property knowledge, it should be deliberately promoted or connected to the appropriate Vault Record such as a Spec, Asset, Document, or Property Record.

---

# 12. Relationship to Work

Tasks / Lists and Work should cooperate without becoming the same system.

A lightweight item can be deliberately promoted:

**Task / Checklist Item → Convert to Work**

When converted, useful context can carry forward:

- title;
- description / note;
- Property;
- related area;
- related Asset;
- creator / requester;
- source list / checklist.

The original item can then show a simple relationship such as:

**Converted to Work**

rather than creating two unrelated active items.

---

# 13. Relationship to Maintenance

Maintenance owns recurring Property care and Standards.

Tasks / Lists should not become a backdoor recurring-maintenance system.

Example:

**Replace HVAC filter every 90 days** belongs in Maintenance.

**Buy two replacement filters** can belong in a List.

**Bring filter from truck tomorrow** can be a Task.

This keeps each system understandable.

---

# 14. Relationship to CAPTURE

Tasks / Lists does not require CAPTURE for ordinary completion.

Checking off **Buy caulk** or **Measure shelf** should remain lightweight.

If a Task becomes real execution requiring work evidence, the user should convert it to Work and use CAPTURE from there.

CAPTURE can still create or attach a quick note / photo to an appropriate list item where useful, but Tasks / Lists should not inherit the full CAPTURE workflow.

---

# 15. Relationship to Calendar and Daily Grind

A Task may have a due date or reminder without becoming a Calendar appointment.

Calendar is used when actual scheduled time matters.

Daily Grind may surface a Property Task, Checklist item, or List reminder when it matters today.

The underlying item remains owned by Tasks / Lists; Daily Grind does not create a duplicate copy.

---

# 16. Search

Search is limited to Tasks / Lists available to the current person at the current Property.

Search can match:

- titles;
- list names;
- item text;
- room / area;
- Asset;
- permitted notes.

Search does not expand permissions.

---

# 17. Permissions

Tasks / Lists follows Property and Record permissions.

Examples:

- Homeowners may create and manage appropriate Property-owned lists;
- Trade Professionals and Trade Team Members may create private/internal lists associated with the Property;
- authorized Business participants may see Business-internal lists according to authority;
- shared lists are visible only to the intended authorized participants;
- Viewers remain view-only where visibility is granted.

Assignment of a lightweight Task does not grant unrelated Property or Business access.

---

# 18. Visual Direction

Tasks / Lists should feel intentionally calmer and lighter than Work.

Visual priorities:

- large working sheet over the Property Timeline;
- simple **Tasks | Checklists | Lists** selector;
- compact rows / cards;
- minimal metadata;
- obvious check-off interaction;
- clear audience language;
- fast add-item flow;
- no dashboard feel;
- no dense status taxonomy;
- no Work-level activity feed unless the item is converted to Work.

The goal is a **well-appointed working pad**, not another project-management screen.

---

## Governing Relationship

**Tasks = small things to remember or finish.**  
**Checklists = groups of steps to work through.**  
**Lists = flexible collections of related items.**  
**Work = jobs that need operational management.**  
**Maintenance = recurring Property care and Standards.**

---

## Governing Rule

**Property Tasks / Lists keeps lightweight Property organization lightweight. When an item grows into a real job, it moves into Work rather than forcing Work-level complexity into the list system.**
